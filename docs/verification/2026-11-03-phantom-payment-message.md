# Phantom payment message compatibility (2026-11-03)

The owner reported `wallet_return_mismatch` after confirming a mainnet SOL payment in Phantom. The client retained the wallet response locally and did not reserve or broadcast it. The exact mutation in that response is not yet independently known; the new safe response code in **Details** can classify it without exposing signed bytes.

Confirmed code-level cause: the previous paid template contained only System transfers. [Phantom's published priority-fee behavior](https://github.com/phantom/docs/blob/master/development-powertools/solana-priority-fees.md) says it may add Compute Budget instructions to dApp transactions without them at signing time, including `signTransaction`. This changes the signed message, so SEJIRE's required exact-message check rejects it. The synthetic extension test reproduces that failure. `signAndSendTransaction` is unsuitable because the application must durably reserve a signature before broadcasting.

New preparations include a fixed Compute Unit Limit (200,000) and Compute Unit Price (zero) before the SOL transfers. `getFeeForMessage` still supplies the actual estimated network fee for this exact message. The server retains the exact-message, recipient, reference, signature and finalized-chain checks. Old transfer-only v1/v2 preparations remain valid for reconciliation; server-fenced renewal of the same immutable order produces the new template only after the previous blockhash expires, reference lookup completes and the ledger excludes a pending reservation/payment. No browser polling opens a wallet.

The first CI attempt exposed a second required detail: web3.js recompiles the message when a signature is filled and sorts writable and readonly account keys. The updated builder matches that canonical order. The SDK regression now fills a signature slot before comparing the wire message, so an unsigned-only roundtrip cannot miss this condition.

The browser regression models Phantom adding a priority instruction to an old preparation, checks no reserve/send, then renews that same order and signs/sends once with the fixed template. Another regression confirms Phantom-style behavior does not mutate a new preparation. Sponsor tests check the SDK wire roundtrip, the two Compute Budget instructions, exact transfers, and validation/renewal of a legacy preparation. Real Phantom and final storage still require owner acceptance. Do not clear the browser journal or approve another transaction while the existing attempt is unresolved.

Before root publication, the deployed Worker returned `ready:false` from the read-only RPC health probe: `getTransaction` rejected a latest finalized Vote transaction with RPC code `-32015` (`unsupported-transaction`). The probe had set `maxSupportedTransactionVersion:0`; Vote history can contain v1 transactions. The health probe now accepts v1 **only for this arbitrary Vote transaction**. Actual SEJIRE payment decoding remains limited to its legacy transaction template. The sponsor runtime mock models a v1 Vote result and asserts the probe option, preventing a repeat of this readiness failure. This evidence does not identify the owner's exact Phantom response.

After publication, the owner reported the safe local code `wallet_message_changed`. That code was inconclusive: the journal retains a wallet response across a server-fenced preparation renewal, but the first diagnostic compared it with the **current** preparation. The diagnostic now stores the exact preparation message alongside future rejected wallet responses and compares those two messages; it also distinguishes a changed blockhash, fee payer, payment instructions and Compute Budget instructions. For older journal records without the original preparation message, a blockhash difference is explicitly ambiguous. These codes remain read-only: they cannot reserve, send, renew or sign anything. Synthetic browser tests cover an appended priority instruction, changed Compute Budget and a legacy journal response after renewal. The actual cause of the owner's retained response still needs the revised safe code from the same browser; no payment should be retried based on the old broad code alone.

The next read-only code from that browser was `wallet_payment_instructions_changed`. Because this older response predates the saved preparation-message field, it only proves a difference against the currently available preparation; it does not identify which instruction property differs or establish that a SOL payment was broadcast. The local classifier now splits the difference into instruction count, program, account count, account address, account flags and data, without revealing addresses or amounts. Synthetic wallet mutations verify that a changed destination or transfer data stays in the journal and causes zero reserve/send calls. Exact-message validation and server payment fencing remain unchanged. Do not ask the owner to approve another transaction based on this code.

The next safe code was `wallet_payment_instruction_count_changed`. The classifier now finds an unchanged copy of every expected payment instruction before identifying any extra instruction by **public program class only**: System transfer, other System instruction, Memo, or another program. It reports missing, multiple extra, or simultaneous count/content changes separately. A synthetic extra System transfer and Memo both leave the order unreserved and unsent. This diagnostic never displays destination, amount, bytes or signature, and never treats any added instruction as an authorized payment.
