# Готовность SEJIRE к публикации: Solana + промокод

Дата проверки: **24 ноября 2026 года, Asia/Almaty**.

## Решение

**Публичный запуск по текущему требованию пока не готов.** Проверенный независимый
пакет исправен, но не содержит оплаты SOL, сохранения по промокоду и админки фонда.
Вход владельца в ar.io Console не устраняет это несоответствие.

Это уточнение относится к последнему запросу владельца: посетитель открывает
`sejire.ar.io`, сохраняет через Solana Mainnet либо промокод, а владелец меняет
промокод в админке. Требование убрать обязательную зависимость от Cloudflare
сохраняется. Предыдущее решение «пакет готов» относилось только к профилю
`decentralized-direct-arweave`, а не к этой совокупности функций.

| Функция | Independent ZIP | Код funded-профиля |

`scripts/static-release-profile.mjs` и emitted `bundle-boundary.json`.
Добавить исключённые компоненты настройкой уже загруженного ZIP нельзя.
`scripts/permaweb-release.mjs` и текущий ручной permaweb workflow также принимают
именно независимый профиль. Нужен отдельный правильно названный funded-профиль
с соответствующими проверками; ослаблять independent contract нельзя.

CI для `17a254e` дополнительно собирает `native-admin-build`, но его Fund URL
содержит `workers.dev`. Наличие этого artifact не является приёмкой сервиса без

отдельному native-пути: ими нельзя объяснять недоступность всех платежей SOL
Mainnet в общем V2 checkout.

## Сервер без Cloudflare

В репозитории уже есть Linux Node/SQLite adapter, использующий существующие
checkout/fund/recipient APIs и ledger. Это основа для замены Worker, но не
подтверждение развёрнутого production сервиса.

В этом проходе существующий `apps/sponsor/tests/linux-server.mjs` прошёл:
сохранение и запуск alarm, общая база, запрет второго writer, одинаковые
order/key/token после обычного перезапуска и синтетический contribution-заказ.
Внешний RPC был подставлен. Полное paid/promo сохранение архива через Linux,
настоящий кошелёк и восстановление в чистом браузере этим тестом не проверены.

### Воспроизведённый дефект аварийного перезапуска

На исходном `17a254e` после `SIGKILL` оставался обычный файл `.writer.lock`.
Повторный запуск с прежней БД завершался `backend_writer_already_active`, хотя
процесс уже умер. Проверка использовала только временную синтетическую БД,
выключенные платёжные функции и запрет внешнего `fetch`.

Исправление подготовлено в отдельной ветке `fix/linux-writer-recovery-20261124`.
Новая версия удерживает SQLite-блокировку внутри постоянного каталога
`<db>.writer.lock`; ядро освобождает её после смерти процесса. Каталог также
блокирует старый способ захвата того же настроенного пути. Обычный legacy
sentinel не удаляется автоматически. Порядок остановки дожидается HTTP,
очередей и фоновой работы до закрытия основной БД и освобождения guard.

Штатный `npm run test:linux --prefix apps/sponsor` прошёл все пять групп,
включая реальные дочерние процессы: запрет второго writer и symlink aliases,
`SIGKILL` и успешный повторный запуск, прежние order/key/token без нового RPC
при повторе запроса, неизменность legacy sentinel, ошибку занятого порта и
один Promise завершения для повторного `close()`. Ревью выполнено отдельно от
автора; `git diff --check` прошёл.

[Лог теста](2026-11-24-sol-promo-readiness/linux-writer-test.log),
[результат и среда](2026-11-24-sol-promo-readiness/linux-writer-result.json),
[границы и переход со старой версии](../LINUX_WRITER_RECOVERY.md).
Это синтетическая проверка уже записанного contribution-заказа, а не реальная
оплата или upload архива. Новый полный GitHub CI после исправления не запускался.
Принятый independent ZIP и исходный `17a254e` остаются неизменными.

Подозрение на unhandled rejection в очереди alarm отдельной синтетической
проверкой не подтвердилось: ошибка была обработана, shutdown завершился.
Исправление такого неподтверждённого дефекта не добавлялось.

### Что остаётся до production

1. Проверить полный paid и полный promo сценарии через выбранный Linux runtime,
   включая перерыв, прежние idempotency keys, реальный readback и восстановление.
2. Назначить и развернуть HTTPS API origin без обязательного Cloudflare,
   проверить policy, CORS, серверную авторизацию, версию и сохранность ledger.
3. Подготовить согласованный перенос прежних обязательств, если используется
   прежняя казна: ciphertext, подписанные байты, резервы, платежи, idempotency,
   promo revision, получатели и alarms. Не запускать два исполнителя одной казны.
4. Проверить права владельца, реальные публичные SOL-получатели, AR-баланс и
   доступный бюджет. SOL-поступления сейчас автоматически не конвертируются в AR.
5. Собрать целевой frontend с SOL + промокодом + админкой, сохранить последние
   исправления редактора/импорта/PDF и автономное восстановление; получить новый
   exact-SHA CI и принятый пакет этого профиля.

При работе через HTTPS reverse proxy текущий adapter видит адрес proxy вместо
отдельных посетителей. Перед таким развёртыванием требуется корректная настройка
ограничения запросов и доверенной передачи IP. Произвольный пользовательский
`X-Forwarded-For` нельзя считать доверенным. Это условие конкретного будущего
развёртывания, а не воспроизведённый отказ действующего сервера.

## Админка и ограничения сохранения

В funded-клиенте существуют маршруты `#/admin`, `#/fund-admin` и
`#/admin/diagnostics`. После правильной публикации целевой адрес фонда будет
`https://sejire.ar.io/#/fund-admin`; главный admin-маршрут —
`https://sejire.ar.io/#/admin`. Это описание маршрутов исходников, а не
подтверждение их наличия в независимом ZIP или готовности нового live сервера.

Fund Admin поддерживает смену промокода с подтверждением, включение/выключение,
лимит фонда, статистику, журнал операций и настройки SOL-получателей. Новый код
должен закрывать старый для новых заказов, сохраняя ранее принятые обязательства.
Счётчик сохранений отражает завершённые заказы, а не уникальные деревья.

Статический `admin-lock.json` защищает только вход в интерфейс. Управление
сервером требует отдельной серверной проверки. Linux adapter не монтирует старые
`/v1/admin/setup` и `/v1/admin/password`; поддерживаемый серверный вход необходимо
настроить и проверить. Вход владельца ArNS через Wander сам по себе не является
входом в админку SEJIRE.

Размер encrypted archive в paid и promo ограничен **524288 байт (512 KiB)**.
В коде обоих путей есть верхняя граница, поэтому увеличение одной переменной
окружения её не снимает. До расширения лимита интерфейс должен отказывать
до оплаты и сохранять локальные данные. Успешная печать дерева на 8191 человека
не доказывает, что его полный vault с историей проходит этот лимит.

## Условия публикации по имени

Публиковать нужно содержимое принятой сборки с Arweave path manifest,
правильными Content-Type, `index.html` и fallback; загрузка ZIP одним файлом
не размещает работающий сайт. Сначала проверяется новый manifest ID и каждый
выдаваемый файл, затем реальная приёмка SOL и промокода, после этого — смена
только корневой записи `@` у уже купленного имени. Предыдущий Target сохраняется
для возврата. Приём upload-сервисом не равен окончательному Arweave settlement.

Требуется восстановление всех деревьев и истории в чистом браузере, проверка
скачанных байтов, длины и SHA-256, а также автономное открытие копии без сайта.
При переходе с GitHub Pages на ArNS данные IndexedDB/localStorage автоматически
не переносятся: прежние локальные копии и незавершённые заказы нужно сохранить.

Статический сайт и автономный формат улучшают долгосрочную доступность чтения.
Сервис новых SOL/promo сохранений всё равно требует работающего исполнителя и
финансирования AR. Публикация фронтенда в Arweave не размещает и не обслуживает
этот сервер автоматически и не является обещанием работы через 200 лет.

Официальные первичные инструкции, проверенные в этой сессии:

- [Arweave path manifests](https://docs.ar.io/build/upload/manifests/).
- [Управление существующим именем в Console](https://docs.ar.io/build/guides/working-with-arns/buy-manage-arns-console/).
- [SPA routing и fallback](https://docs.ar.io/sdks/ario-deploy/single-page-apps/).
