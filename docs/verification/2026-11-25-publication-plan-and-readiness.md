## Как работает подготовленный релиз

После публикации статические HTML, JavaScript, стили и автономный recovery kit размещаются в Arweave. Отдельный переносимый Linux-сервис принимает и проверяет операции SOL/промокода, ведёт SQLite-журнал и продолжает принятые задания. После закрытия вкладки продолжение обеспечивает работающий сервис. Это требует постоянного хоста, сохранения диска и финансирования AR-казны.

Сервисная плата посетителя — 30000000 lamports (0.03 SOL), комиссия Solana показывается отдельно. Дальнейшая запись зашифрованного архива оплачивается AR из фонда. Получение сервисной платы в SOL не пополняет AR-казну автоматически; обмена SOL → AR в этом процессе нет. Промокод освобождает посетителя от сервисной платы, но расходует AR фонда. Изменение промокода не отменяет ранее принятое обязательство. Добровольный взнос включается владельцем отдельно; при включении он доступен отдельным действием и по умолчанию равен нулю. Максимальный зашифрованный envelope текущего профиля — 524288 байт (512 KiB).

Новые предложения публичного интерфейса `portable-funded-mainnet` используют Mainnet. Режимы приёма legacy API инвентаризируются отдельно: это не утверждение об удалении всех старых Devnet-путей из сервера. Ранее сохранённые исторические policies и операции, включая Devnet, сохраняются для продолжения и сверки. Серверный кошелёк не получает приватный ключ посетителя. Повтор после сетевой неопределённости использует прежние зафиксированные подпись и байты; новая подпись/оплата не подставляется автоматически.

## Порядок запуска

### 0. Закрыть текущий сетевой release gate

Получить успешную свежую проверку двух настроенных native API и повторить полный CI того же source. Затем принять единственный подходящий portable artifact по source SHA, run/attempt, времени создания, ZIP digest и всем файлам. Если source или API origin изменяется, нужен новый commit и полный CI. Частичные успехи, диагностическая ветка, локальная папка и артефакт предыдущего упавшего кандидата не подходят как accepted release.

### 1. Выбрать и подготовить постоянный хост

Нужен Linux/Docker, HTTPS, постоянный `/data`, один SQLite writer, один исполнитель, дисковое место и защищённая копия на другом хосте. В репозитории подготовлены Dockerfile, Compose и закрытый по умолчанию шаблон конфигурации. Первое подготовительное включение выполняют только с отдельной **пустой базой**, без импортированных заказов, и с выключенными флагами приёма/исполнения из шаблона. Оно проверяет процесс, диск и HTTPS и не заменяет миграцию.

Эти флаги не являются общей остановкой прежних обязательств: после запуска импортированной базы существующие promo jobs могут продолжаться при выключенном приёме новых заказов. До проверенной передачи единственному исполнителю импортированную базу держат с review marker, а процесс, который должен её обслуживать, — остановленным.

Бесплатный спящий хост не подходит для фонового завершения сохранений. Если используется уже рассмотренный Blitz, конкретный тариф/режим должен обеспечивать always-on; его платное включение и billing выполняет владелец. Повторное read-only чтение аккаунта 25 ноября подтверждает Free и отсутствие SEJIRE app; подписка не оформлена. Возможен другой постоянно работающий Linux-хост, при этом адрес API сначала согласуется со сборкой клиента.

### 2. Перенести старое состояние и исполнение

Для export-only entry и compatibility proxy готовится **отдельный операторский пакет**. Он не является частью feature-релиза и его CI, не развёрнут и требует собственной проверки и отдельного действия владельца на прежнем сервисе. Операторский source commit: `7eb522e6cae947132f792a010312a7a6c41ddb19`, отдельная ветка `docs/funded-release-evidence-20261125`. [Инструкция и код](https://github.com/azovskaya/sejire_arweave_solana/tree/7eb522e6cae947132f792a010312a7a6c41ddb19/deployment/legacy-export); [evidence](../../deployment/legacy-export/evidence/summary.json): 15 синтетических групп PASS, TypeScript PASS, пофайловые SHA. Реальный Cloudflare upload API и production snapshot не проверялись; результаты CI публичного приложения их не заменяют.

Подтвердить действительный старый Worker, namespace, fixed Durable Object и deployed source. После проверки операторского пакета владелец заменяет entry именно прежнего Worker, сохраняя identity класса/namespace/object, на режим `MAINTENANCE_EXPORT_ONLY`. Подтвердить принятие новой версии всем трафиком и завершение старых in-flight операций; только после этого выполнить отдельный `POST /__sejire_legacy_export/seal-quiescence` с актом `SOURCE_EXECUTION_STOPPED`. До seal выгрузка snapshot блокируется. Операторский пакет не выполняет deployment и не доказывает остановку внешних исполнителей автоматически.

Для закрытого экспорта владелец задаёт отдельный временный `SEJIRE_EXPORT_TOKEN`: 32 случайных байта в виде 64 lowercase hex-символов. Это не `ADMIN_TOKEN`; он передаётся только в защищённом `Authorization`-заголовке операторского клиента и приватном файле `0600`, не через браузер, URL, чат или Git.

Выгрузить частный snapshot и проверяемую sidecar-квитанцию. Пустой `getAlarm()` сам по себе не доказывает отсутствие прежнего alarm: требуется отдельная зафиксированная сверка alarm и обязательств владельцем по инструкции операторского пакета.

Импортировать снимок только в **новый ещё не существующий путь SQLite**, отдельно от пустой подготовительной базы шага 1. Сверить таблицы, counts, hashes, rowids, capability hashes, ciphertext, unsigned/signed bytes, holds, spent, ceiling, бюджеты и старые квитанции. Восстановление/импорт создаёт обязательный review marker. До завершения сверки и следующего шага marker сохраняется, а новый исполнитель не запускается. Команда подтверждения является записью решения оператора, а не доказательством блокчейн-сверки.

Legacy KV `/v1` и отдельные экспериментальные protocol journals требуют самостоятельной инвентаризации. Они не становятся автоматически частью SQLite и не покрываются планируемым proxy для `/api/checkout` и `/api/fund`. Старый frontend origin и его API должны оставаться пригодными для уже начатых заказов; действие по сохранению прежнего API URL описано в шаге 4. Смена адреса сайта не переносит browser storage между origins; токены доступа не передают в ссылках.

Прежнее обязательство `AtwLYx509C9jWIFKUNg7dy1GSgiaDbXVK1YEQbBWfHY` сохраняется отдельно: ожидаются 25269 байт, SHA-256 `96bb194c3fbcf1dfea7e738cf91d758b8cfdaabb5be934df8dacd96a65c7be85`. Новое подтверждение доступности полного ciphertext не получено. Не создавать новый платёж или новый архив вместо восстановления исходной операции.

### 3. Проверить резервирование и передачу единственному исполнителю

До включения нового приёма проверить частную резервную копию импортированного состояния, её `quick_check`, SHA-256 и копию на другом хосте. Выполнить пробное восстановление в отдельный новый путь, сверить данные и проверить блокировку запуска до reconciliation. Восстановленная учебная копия остаётся остановленной; она не становится вторым исполнителем с тем же signer. Резервная копия на том же диске не заменяет off-host копию.

Только после содержательной сверки миграции, резервной копии/восстановления и подтверждённой остановки прежних исполнителей владелец фиксирует передачу единственному Linux executor и снимает review marker выбранной рабочей базы штатной командой подтверждения. Остановить подготовительный процесс шага 1, задать `SEJIRE_LINUX_DB` равным точному пути проверенной импортированной базы и использовать этот путь при следующем запуске. Не удалять marker вручную и не запускать одновременно рабочую и восстановленную копии.

После запуска рабочий сервис с настроенным `SEJIRE_BACKUP_DIR` создаёт online SQLite snapshots. Проверить реальное появление копий и их перенос на другой хост. Регулярно контролировать здоровье API, свободный диск, возраст последней независимой копии, AR-фонд и незавершённые задания.

### 4. Настроить API и админку, затем выполнить final preflight

В защищённую среду владельца передаются `ADMIN_TOKEN`, прежний `PROMO_CODE_SECRET` и правильный `ARWEAVE_TREASURY_JWK`. Они не публикуются в Git, клиентском JavaScript, Arweave или чате. Публичный AR signer текущего профиля — `qgoIFw9WsusMRapWzcFg4jNW08HSWvQkpAKOz86BUuI`; paid и promo используют соответствующую общую физическую казну.

Владелец подтверждает два разных публичных SOL-адреса — сервисная плата и добровольная помощь. Устанавливаются прежний budget ID, проверенные AR-лимиты, два работоспособных Mainnet RPC, точные CORS origins и документированные trusted proxy CIDRs. `CHECKOUT_SOLANA_RPC_URLS` принимает JSON-массив URL (до четырёх), а не строку через запятую. Приватный RPC token остаётся на сервере.

`CHECKOUT_ALLOWED_ORIGINS` содержит точные origins через запятую без пробелов. При незаданном trusted proxy пользовательский `X-Forwarded-For` игнорируется; нельзя подставлять доверие ко всему интернету.

Установить `SEJIRE_BUILD_COMMIT` равным точному SHA развёрнутого исходного релиза и сопоставить его с историей сборки хоста. После выполнения шагов 2–3 запустить API с выбранной импортированной базой, сохраняя флаги нового приёма выключенными до проверки настроек. Этот запуск уже может продолжать ранее принятые обязательства; прежний исполнитель к этому моменту остановлен.

**До final preflight открыть админку на точном CI-пакете.** Скачать именно `permaweb-portable-funded-release` успешного полного CI. Сверить ZIP digest, source SHA, profile и hashes всех файлов. Открыть неизменённую папку на временном HTTPS origin или локально:

```bash
python3 -m http.server 8080 --bind 127.0.0.1 --directory ПАПКА_ПРОВЕРЕННОГО_ПАКЕТА
```

Для localhost временно установить `CHECKOUT_ALLOWED_ORIGINS=https://sejire.ar.io,http://127.0.0.1:8080`, сохранив также необходимые проверенные origins прежних клиентов. Админка открывается по `http://127.0.0.1:8080/#/admin`. Для HTTPS preview используется его точный origin и тот же путь `/#/admin`; он должен быть доступен устройству для мобильной приёмки. Не открывать `file://` и не подменять пакет dev-сервером/другой сборкой. Встроенный адрес API не меняют.

Войти с `ADMIN_TOKEN`, открыть «Промокод и фонд», сверить импортированные revision, состояние кода, историю, лимит, расходы и резервы. Действующий импортированный код не нужно менять только ради переноса. Если код отсутствует или владелец решил его заменить, нажать «Изменить промокод», дважды ввести новый код, сохранить и проверить серверное подтверждение/новую ревизию. Включить промокод после готовности миграции и резервного копирования; проверить readback. Сам `PROMO_CODE_SECRET` — серверный HMAC-секрет, а не код, который вводит посетитель.

Если недостаточен учтённый AR-остаток, в этой же вкладке открыть «Пополнение фонда AR». Сначала указать сумму и нажать **«Подготовить пополнение»**, дождаться подтверждённой заявки и её реквизитов. Затем подключить Wander с другим собственным AR-кошельком, проверить Arweave Mainnet, получателя, точную сумму, обязательный тег и комиссию; подписать один перевод и отдельной кнопкой отправить сохранённую подпись. После не менее 12 подтверждений нажать «Проверить и учесть пополнение» и сверить результат. Обычный перевод без тега новой заявки не подходит для увеличения учтённого ceiling. Лимит промофонда меняется отдельно: повышение лимита не переводит AR, а зачисление AR не повышает этот лимит автоматически. При неизвестном результате продолжать ту же заявку/сохранённую транзакцию, не запрашивать новый платёж.

После готовности миграции, единственного исполнителя, резервного копирования и настроек фонда владелец явно включает необходимые для текущего preflight флаги и применяет конфигурацию сервиса:

```text
CHECKOUT_API_ENABLED=true
CHECKOUT_PAID_ENABLED=true
CHECKOUT_PAID_EXECUTION_ENABLED=true
FUND_API_ENABLED=true
```

Отдельно проверить, что импортированный или заданный промокод включён. `CHECKOUT_CONTRIBUTION_ENABLED` остаётся отдельным решением о добровольных взносах и не включается автоматически. Сохранённые legacy admissions и их policy-настройки сверяются по инвентаризации шага 2.

Выполнить `npm run portable:service:verify` с защищённо переданным `SEJIRE_PREFLIGHT_ADMIN_TOKEN`, `SEJIRE_FUNDED_API_ORIGIN` и `SEJIRE_EXPECTED_SERVICE_COMMIT`. Проверка делает только чтение и OPTIONS: exact source, закрытая админка, Mainnet, 0.03 SOL, четыре флага, включённый промокод, CORS, signer, quote полного 512 KiB архива и доступный фонд после holds/ceiling. Она не создаёт заказы и не доказывает реальный wallet roundtrip. Production preflight проверяет CORS для `https://sejire.ar.io`; фактический временный origin дополнительно проверяется в браузере.

Если прежние клиенты используют старый API URL, после готовности нового API и передачи единственному исполнителю владелец отдельно развёртывает проверенный compatibility proxy по прежнему адресу. Он направляет поддерживаемые `/api/checkout` и `/api/fund` к Linux без второго signer/executor, redirect или автоматического повторения запроса. До завершения переключения проверить CORS старого frontend origin, продолжение прежнего capability/order и фактические ingress/rate limits. `/v1` и отдельные protocol journals этим не решаются. Развёртывание proxy остаётся невыполненным действием отдельного операторского пакета.

### 5. Реальная приёмка до загрузки сайта в Arweave

Использовать тот же неизменённый CI-пакет и временный origin из шага 4 после успешного final preflight.

На синтетической семье выполнить настоящий Mainnet SOL-платёж 0.03 SOL плюс показанная кошельком комиссия и отдельное сохранение по промокоду. В обоих случаях проверить receipt, transaction ID, фактически доступные raw bytes, размер, digest и восстановление в чистом браузере и автономным decoder. Проверить вход/выход администратора, изменение кода, отказ старого кода для новых сохранений и продолжение уже принятой операции после изменения кода. После приёмки удалить временный CORS origin. Сохранить частный recovery kit тестовых операций.

### 6. Подготовить и загрузить неизменённый статический пакет

Загружается только статическая папка с `index.html`, assets, `404.html` и recovery kit. Исходный репозиторий целиком, backend, SQLite, snapshots, `.env` и ключи не являются содержимым сайта.

Для Actions-пути подготовлен draft PR № 12: он регистрирует ручной `permaweb-portable.yml` в default branch. Пока PR не слит, кнопка manual workflow ещё не гарантирована. Слияние регистрации само upload не запускает. После регистрации выбирается точная release feature branch. Режим `prepare` получает проверяемый пакет и quote без кошелька. Его успех не доказывает deployment API или production-приёмку.

После успешного полного CI заполнить форму по принятому релизу. **Сейчас принятый run отсутствует; запуск prepare/upload не должен обходить этот отказ.**

Отметки о миграции, always-on/restore и реальных сохранениях — решения владельца; workflow не подменяет их автоматическим доказательством. Автопополнение credits отсутствует; неоднозначный upload нельзя автоматически повторять с новой подписью. Возможность загрузки подготовленной папки через Console рассматривается отдельно по фактическому интерфейсу и сохраняет те же проверки пакета, manifest, стоимости и публичных байтов.

#### Вариант с ключом только внутри Wander

Официально описан [ArDrive Web](https://app.ardrive.io): подключить существующий Wander, выбрать публичный drive, загрузить всю принятую папку через Upload Folder, создать manifest этой папки и получить Data TX ID. Назначение существующего имени можно отложить до проверки. Для этого способа не требуется экспортировать JWK в GitHub.

Проверить raw manifest по `https://turbo-gateway.com/raw/MANIFEST_TX_ID`: корневой index, все относительные paths, assets и recovery kit, а также `fallback.id`. Затем сверить опубликованные bytes с CI. Официальные UI-инструкции не подтверждают настройку fallback; наличие `404.html` не заменяет это поле. Если manifest не соответствует release-контракту, этот способ ещё не принят: нужен отдельно проверенный корректный manifest, до смены Target.

Точные кнопки folder deploy в Console не подтверждены просмотром живого интерфейса. ArDrive-путь не выполняет автоматические GitHub upload gates: все проверки API, миграции, реальных сохранений, пакета и стоимости остаются обязательными.

Источники: [ar.io deployment guide](https://docs.ar.io/build/guides/hosting-decentralised-apps/hosting-with-ardrive/), [вход с Wander](https://ardrive.io/help/using-ardrive-apps-getting-started-log-into-ardrive-arconnect/), [ArDrive manifest и raw inspection](https://ardrive.io/help/using-ardrive-apps-using-ardrive-create-an-arweave-manifest/).

### 7. Проверить опубликованную версию по manifest TX ID

Сначала открыть новую версию по transaction URL. Сверить manifest paths, Content-Type, `index.html`, стили/модули, fallback, deep hash-ссылки и точные файлы recovery kit. Проверить отображение на desktop/mobile и встроенный адрес API. Эти проверки публичных файлов не означают, что API разрешает запросы с origin transaction URL.

После удаления preview origin API по умолчанию разрешает `https://sejire.ar.io` и отдельно сохранённые origins прежних клиентов. Если до переключения имени нужно проверить SOL/promo/admin именно из transaction URL, владелец временно добавляет **точный origin этого URL** в `CHECKOUT_ALLOWED_ORIGINS`, проверяет работу и удаляет временное разрешение. Путь с transaction ID не является частью origin; wildcard не используется. Без такого разрешения отказ API по CORS ожидаем и не подтверждает поломку опубликованных файлов. Только после проверки пакета и завершённой приёмки шага 5 разрешать переключение имени.

### 8. Переключить существующее имя

Открыть `https://console.ar.io/domains/sejire`. Убедиться, что текущая авторизация действительно даёт Owner/Controller права. Сохранить прежний корневой `@` Target и TTL. В разделе Records выбрать карандаш строки `@`, вставить новый **manifest transaction ID**, проверить показанную операцию и подтвердить её в своём кошельке. Повторно покупать имя не требуется.

После смены проверить `https://sejire.ar.io`, прямые hash-ссылки и обычное/приватное окно. Учесть TTL кеша. Для отката интерфейса вернуть прежний Target; новый сервер продолжает обслуживать все уже принятые обязательства. Возврат имени не удаляет новые публикации и не откатывает финансовый журнал.

## Что потребуется от владельца

В чате достаточно несекретных данных: выбранный хост/тариф и финальный API-домен; подтверждённые публичные SOL-адреса; фактические идентификаторы прежнего сервиса и source version; видимые Owner/Controller и старый Target имени. Частный snapshot, токены, JWK, promo HMAC secret и пароль администратора передаются только через защищённые средства на хосте владельца. Восстановительные слова кошелька вводятся владельцем внутри собственного кошелька, не в чате или поле сайта.

Для реальной приёмки нужен кошелёк владельца с 0.03 SOL плюс комиссией, достаточно учтённых AR и доступного бюджета для двух тестовых архивов и последующих пользователей. При необходимости пополнения нужен другой собственный AR-кошелёк для описанного в шаге 4 перевода через Wander с комиссией. Для Actions-загрузки сайта нужны отдельно согласованный upload quote, существующие credits загрузочного кошелька и два указанных GitHub Secrets. Деньги SOL, AR и credits загрузки не объединяются в один условный баланс.
