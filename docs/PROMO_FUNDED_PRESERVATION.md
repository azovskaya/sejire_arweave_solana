# Promo Funded Preservation

This feature adds one editable promo code to SEJIRE's existing encrypted-envelope preservation path. A valid code skips the user's Solana payment and asks the SEJIRE Worker to sign an Arweave Mainnet storage transaction. The existing Solana checkout is separate and unchanged. The archive contains only the existing `sejire/envelope/v1` ciphertext; recovery words and decrypted family data never enter the Fund API.

## Deployment and keys

The treasury is the **existing** Arweave address `qgoIFw9WsusMRapWzcFg4jNW08HSWvQkpAKOz86BUuI`. No wallet or separate 13 AR account is created. The Worker requires `ARWEAVE_TREASURY_JWK` as a protected server secret and verifies that it derives to this exact address before signing. It never reads a local JWK file. Do not paste the JWK into Admin, Pages, `VITE_*`, `.env.example`, source, fixtures or browser storage. `PROMO_CODE_SECRET` is a separate random 32+ character Worker secret for HMAC-SHA256. The existing Worker `ADMIN_TOKEN` or existing server Admin password in KV protects management endpoints. The static `admin-lock.json` check alone is not a server authorization mechanism. The Fund tab asks separately for a server credential and keeps it in component memory only; it never sends the static Admin login password automatically. Public address and live balance load when Admin opens without any credential.

`FUND_API_ENABLED` defaults to `false` in Wrangler. First production setup needs explicit owner authorization to deploy the Worker with its SQLite Durable Object binding, set the two secrets manually, configure `CHECKOUT_ALLOWED_ORIGINS`, and connect the public Pages build to the Worker through `VITE_FUND_API_URL` (public URL only). Keep `FUND_API_ENABLED=false` until this setup and review are complete. No deployment or live transaction was performed during development.

With the flag off, new `/validate` and `/orders` POST requests remain closed. The authenticated Admin dashboard and `GET /api/fund/admin/readiness` remain available for rollout checks and reconciliation. Readiness derives the signer address inside the Worker, compares it to the fixed public treasury address, fetches the live balance and a 6144-byte quote, and returns only public values. It never prepares, signs or submits a transaction. A mismatch returns `treasury_address_mismatch`; the dashboard marks an unverified signer as `PROVIDER ERROR`. Existing order polling remains available so an interrupted operation can still be reconciled if the flag is switched off.

The Worker uses the existing `CHECKOUT_LEDGER` SQLite Durable Object and a single global object name. It stores settings, an immutable order row, append-only status events, rate buckets and Admin audit events. The initial cumulative limit is **13,000,000,000,000 winston = 13 AR**. Admin may change it at runtime; changing the limit never resets ledger spend or tree counts. Lowering below confirmed spend or confirmed spend plus active reservations is rejected.

## Single promo

Admin submits and confirms one new code. The Worker normalizes `trim().toUpperCase()`, stores only `HMAC-SHA256(PROMO_CODE_SECRET, normalizedCode)` plus a display hint, and increments `promoRevision`. The old code immediately stops validating. There are no vouchers, campaigns, eligibility records or user accounts. The Admin may enable or disable the current code. Admin audit records `PROMO_CHANGED`, `PROMO_ENABLED`, `PROMO_DISABLED`, `FUND_LIMIT_CHANGED` and `FUND_RECONCILED` with revisions or old/new limits, never code plaintext.

## Reservation, upload and accounting

1. The browser serializes the already encrypted envelope. The Worker validates its strict schema, maximum 512 KiB size, exact canonical bytes, digest and vault ID. It also rate limits validation and upload per Cloudflare ingress IP. No client supplied price, reward, status or Arweave TX ID is accepted.
2. The server gets current price and live wallet balance, prepares the exact transaction to sign and atomically reserves the prepared reward in SQLite. The reservation includes the order ID, digest, size, vault ID, promo revision and prepared transaction. All money is decimal winston strings or `BigInt`.
3. The server signs with the protected JWK, then durably writes the signed transaction and its ID **before** POST. A retry with the same order cannot sign a different transaction. A retry or reconciliation may submit the same signed TX ID again after checking network status.
4. After network confirmation, the Worker reads the transaction's `reward` field and retrieves the raw archive. It checks byte length, SHA-256 and vault ID. Only then it writes `COMPLETED` and its actual reward. Unknown submit outcomes retain the reservation as `NEEDS_RECONCILIATION`; they are never interpreted as an unpaid order. An unsigned operation is released on a definite signing failure, or by reconciliation after ten minutes with no signed ID; no POST is possible without a persisted signed ID.
5. The Admin's actual spend is `SUM(actualRewardWinston)` for completed orders. Saved trees are `COUNT(COMPLETED)`. Pending signed or reserved orders hold their budget. The ledger events are append-only; displayed aggregates are recomputed from the latest event for every order. A duplicate callback or POST cannot add a second completion.

The budget remaining is `max(0, limit − confirmed spend − active reservations)`. Effective availability also subtracts active reservations from the live wallet balance before taking the minimum. This is conservative while signed transactions are not yet mined. Dashboard balance is fetched live from `arweave.net` with `ar-io.dev` fallback; failure displays *Balance unavailable*, never zero. The current price estimate uses the average successful archive size when available and a labelled 6 KiB reference quote before history exists. Estimated remaining tree count uses the larger of historical average actual reward and that live quote; before any completed trees it shows *Not enough data yet*.

Admin Reconcile checks unresolved signed transactions using their saved IDs, network status/reward and raw archive integrity, then recomputes all metrics from the ledger. It processes up to ten pending records per request; Admin reports remaining pending records and may run it again. Completed records are not silently changed. The audit timestamp is updated after each pass. After a reload, the user reselects the same encrypted archive; the browser polls its existing order ID. The order ID is stored in `sessionStorage` under an archive digest; the promo code is not persisted. An archive change starts a different local key and the server rejects reuse of the previous order ID with changed bytes.

## Privacy and limits

Fund history stores technical IDs, archive digest, vault ID, encrypted byte size, promo revision, reward and TX ID. No names, tree titles, dates, relationships, recovery words, plaintext JSON or promo plaintext are stored. Arweave itself receives only ciphertext and technical tags. The shared treasury also signs the permaweb site: a compromise of that key could drain the fund and authorize future site uploads. The previously published immutable site transaction cannot be rewritten, but this key overlap is a significant operational risk. A protected secret and strict Worker route gating are required before activation.

The current Pages V2 paid path remains a fixed pilot archive. The promo branch accepts a general encrypted envelope produced by the existing editor and reuses the existing envelope/recovery format; it does not create a second archive protocol. Real Worker/Chrome deployment and extension acceptance remain separate owner approved checks. A local mock provider and SQLite tests do not prove Arweave acceptance, finality or gateway propagation.

## Verification

Use Node 22+ on a supported OS. `npm run test:fund` runs a local SQLite and mock provider suite with no network calls or funds. `npm test`, `npm run check --prefix apps/sponsor`, `npm run lint --prefix apps/web`, `npm run web:build`, and the existing Playwright commands cover the rest of the application. Browser tests and real extension acceptance must be repeated on a supported host before enabling the Worker.

Reference API and transactional storage behavior: [Arweave HTTP API](https://docs.arweave.org/developers/arweave-node-server/http-api), [Cloudflare SQLite Durable Object storage](https://developers.cloudflare.com/durable-objects/api/sqlite-storage-api/).

## Linux Worker runtime acceptance

`npm run test:fund-runtime` builds a test-only Worker entry and runs Miniflare/workerd with a real SQLite Durable Object. It sends HTTP requests through the Worker runtime, uses only `MockFundedArweaveProvider`, and starts a new process against the same on-disk SQLite state to verify persistence. The test checks disabled-by-default gating, server Admin credentials, promo rotation, cumulative limit, reward accounting, atomic concurrent reservations, duplicate orders, reconciliation of the same signed TX ID, dashboard metrics and privacy boundaries. The GitHub Actions workflow `.github/workflows/promo-fund-runtime.yml` runs it on Ubuntu with Node 22; it contains no production wallet secret or deploy step. A local Linux Docker run passed 14 runtime checks on 16 October 2026. The GitHub Actions run remains pending until the feature branch is explicitly pushed.
