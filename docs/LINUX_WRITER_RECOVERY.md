# Linux checkout: один исполнитель и восстановление после аварии

Этот документ относится к `apps/sponsor/linux-server.mjs`. Он не включает
платежи, загрузки, миграцию production-данных или публикацию сайта. Для нового
SOL/promo выпуска по-прежнему нужны отдельные настройка и сквозная приёмка.

## Как удерживается право записи

Рядом с каноническим путём ledger создаётся постоянный каталог
`<ledger>.writer.lock`, внутри него — `guard.sqlite`. Единственный процесс
удерживает `BEGIN IMMEDIATE` в этой отдельной SQLite-базе всё время работы.
Проверка выполняется до открытия и инициализации основной базы.

Другой новый процесс не получает SQLite-lock и отказывает с
`backend_writer_already_active`. Ядро освобождает блокировку при завершении
процесса, включая `SIGKILL`, поэтому для повторного запуска не требуется
удаление файла или предположение о том, жив ли прежний PID.

При штатном закрытии сначала завершаются HTTP-запросы, уже поставленные alarm
и фоновые задачи, затем закрывается основная БД, затем guard. Повторный вызов
`close()` возвращает тот же Promise завершения. Неудачный `listen()` также
проходит эту очистку.

Каталог и `guard.sqlite` **никогда не удаляются адаптером**. Их удаление или
подмена при работающих процессах может создать другой inode и нарушить
исключение двух исполнителей. Это не временные файлы для периодической очистки.

Используется локальная файловая система с корректной поддержкой SQLite locks.
Не размещать ledger/guard на сетевой файловой системе и не запускать независимые
копии одной казны на разных компьютерах. Этот guard не является распределённым
лидерством или защитой от второго сервера с копией БД.

## Переход со старого адаптера

Старый адаптер создавал обычный файл `<ledger>.writer.lock` через `open('wx')`.
После аварии этот файл оставался и блокировал перезапуск. Новая версия при
обнаружении такого **обычного файла** отказывает и ничего не удаляет.

Порядок перехода под контролем владельца сервера:

1. Остановить прежний сервис и отключить его автоматический повторный запуск.
   Убедиться, что прежних исполнителей не осталось; простого наличия или
   отсутствия PID-файла недостаточно.
2. Сохранить согласованную резервную копию ledger и незавершённых обязательств.
   Не создавать второй активный backend из этой копии.
3. Только после подтверждённой остановки прежнего сервиса отдельно архивировать
   его обычный sentinel. Не выполнять безусловное удаление lock в startup-скрипте.
4. Запустить новый адаптер с тем же согласованным путём БД. Он создаст постоянный
   каталог на месте старого sentinel и получит kernel-held SQLite lock.
5. Проверить чтение прежних заказов и штатный перезапуск. Сетевые подписи и
   новые оплаты не требуются для проверки сохранности журнала.

Постоянный каталог также мешает прежнему `open('wx')` снова захватить **тот же
настроенный путь**. Все новые процессы канонизируют symlink пути к БД и её
каталогу; hard-linked ledger и guard отклоняются. Старый бинарник не выполнял
такую канонизацию: нельзя запускать его параллельно через другой alias. Во время
миграции старые исполняемые файлы и их supervisor должны быть выведены из работы.

## Проверка без денег и внешней сети

Из корня репозитория с установленными lockfile-зависимостями:

```sh
npm run test:linux --prefix apps/sponsor
```

Существующий тест проверяет SQLite alarm, инициализацию, сохранение
идемпотентного синтетического contribution-заказа после штатного перезапуска.
Добавленная процессная регрессия проверяет:

- отказ второго живого процесса, включая symlink alias БД и её каталога;
- `SIGKILL` первого процесса и последующий успешный запуск с той же БД;
- чтение прежнего заказа по прежним key/token и повтор того же запроса без
  нового заказа или RPC preparation;
- сохранение межверсионного запрета старого `open('wx')`;
- отказ при обычном legacy sentinel без изменения его содержимого;
- освобождение guard после неудачного `listen()` и общий Promise `close()`.

HTTP работает только через loopback. Запросы к разрешённым в фикстуре Solana
RPC подставляются в памяти; любые другие внешние fetch отвергаются. Настройки
и заказы синтетические, ключей AR и реальных переводов нет. Сценарий SIGKILL
проверяет восстановление уже записанного заказа, а не прерывание реального
платежа, подписания AR или загрузки архива.
