# Независимый выпуск SEJIRE

Актуальный порядок от **27 ноября 2026**. Он реализует решение владельца:
приложение и новые архивы работают через Arweave без обязательного сервиса SEJIRE.
Подготовленный код и успешный CI не означают, что сайт уже загружен или имя изменено.

Этот документ относится к профилю `decentralized-direct-arweave`, который собирает
`npm run arns:build`. Рабочая ветка приложения —
`feat/arweave-only-protocol-20261127` (решение владельца от 27 ноября 2026).
`npm run web` и `npm run web:build` также выбирают этот профиль по умолчанию.
Прежние инструкции SOL/Worker/Linux/Blitz описывают
другой профиль и сохраняются для совместимости и ранее оплаченных обязательств.

## Что входит в приложение

Редактор, шрифты, PDF-экспорт, криптография и автономный набор восстановления
публикуются как статические файлы. Новое сохранение архива использует совместимый
Arweave-кошелёк владельца и native Arweave HTTP API. Сервис SEJIRE, Cloudflare
Worker, казна проекта, SOL checkout и bundler не являются обязательными частями
этого runtime. Неиспользуемый внешний PDF-viewer исключается при независимой
сборке; обычное скачивание PDF сохраняется.

Новое сохранение оплачивается **самим пользователем в AR**, по цене выбранного
Arweave-узла. Прежний сбор 0.03 SOL и общий промокод здесь не применяются.
Публичная статическая страница не может хранить секрет казны: автоматическое
спонсирование требует отдельно реализованного и проверенного протокола,
которого этот выпуск не объявляет готовым. Старые операции, квитанции и код
совместимости сохранены. Страница `#/protocol` объясняет действующую модель;
старые `#/admin` и `#/fund-admin` открывают это объяснение. Парольной серверной
админки в новом приложении нет. Управление именем выполняется владельцем в Console.

Сеть Arweave, доступный узел и кошелёк нужны для новой сетевой записи. Шлюзы
заменяемы; доступность одного домена не означает доступность остальных. Настройка
публичного HTTPS-узла доступна в интерфейсе. Не объявлять живой failover проверенным
только потому, что в конфигурации перечислены несколько адресов.

Текущие native API по умолчанию — `arweave.net` и `turbo-gateway.com`.
Последний используется как заменяемый шлюз native Arweave, без bundler API,
аккаунта Turbo или его кредитов. Блокирующая read-only проверка перед выпуском
требует два доступных адреса: `/info`, `/tx_anchor`, `/price` и CORS preflight
для `/tx` и `/chunk`. Это снимок доступности, а не доказательство независимых
операторов, реальной доставки chunks или финального settlement.
Пять запросов к одному узлу выполняются последовательно, а два узла проверяются
параллельно. Так probe не создаёт всплеск новых TLS-соединений к одному адресу;
порог готовности и проверки TLS, сети и CORS не ослабляются.
Native API описан в официальных разделах
[transactions](https://docs.ar.io/apis/ar-io-node/transactions/) и
[chunks](https://docs.ar.io/apis/ar-io-node/chunks/).

### Свой узел

Указанный в сохранении или восстановлении HTTPS-адрес применяется после явного
действия пользователя и сохраняется в `sessionStorage` текущей вкладки. Он
переживает её перезагрузку и используется также при открытии версий, подготовке
следующего сохранения и проверке уже подписанной операции. Ввод текста сам по
себе настройку не меняет. Чтобы вернуться к узлам по умолчанию, очистить поле и
повторить явное сетевое действие. Настройка ограничена сессией вкладки и origin;
она не синхронизируется между вкладками или адресами. В новой сессии её нужно
выбрать снова. Формат автономных файлов и переносимых квитанций не привязан к
адресу узла.

При выбранном своём узле автоматического перехода к публичным адресам нет.
Поиск версий обращается только к его `/graphql`; если такого индекса нет, остаются
восстановление по известному ID и локальному файлу. Поддержка native API нужна
для сетевого сохранения, а не для автономной расшифровки файла. Неверная или
недоступная сохранённая настройка останавливает сетевое действие; ошибка записи
настройки не меняет семейный архив и не означает выбора узлов по умолчанию.

## Правила сохранности данных

- Отказ от открытия версии не меняет draft, полный vault, слова или родительский ID.
- Принятая версия сохраняет все деревья и историю. Метки локальных копий не
  объявляются сетевыми transaction ID.
- Сетевые версии перед использованием проходят проверку native signature, ID,
  Merkle root, метаданных и шифротекста. Индексы служат для поиска кандидатов.
- Явно открытая локальная/файловая копия остаётся выбранным полным архивом.
  Незавершённая локальная подготовка не заменяется старым сетевым снимком.
  Выбор вкладки привязан к SHA-256 канонического зашифрованного envelope.
  Если другая вкладка заменила общий cache, нужна повторная явная загрузка
  нужной копии. Старые локальные сессии без этой привязки тоже требуют
  повторного открытия; черновик при отказе остаётся доступен.
- Намерение подписи записывается до запроса кошелька. Известный окончательный
  отказ позволяет новое явное действие; timeout и неизвестная ошибка не разрешают
  автоматически запросить подпись снова.
- Подписанные байты записываются до отправки. Продолжение использует тот же ID,
  ту же подпись и все chunks, включая архив размером в один chunk.
- Успех требует подтверждённого заголовка и фактических скачанных байтов,
  совпавших по длине и SHA-256. Проверка состояния сама не отправляет архив.

## Три разных решения о готовности

| Решение | Необходимое доказательство |
| --- | --- |
| Код проверен | Полный успешный CI для точного source SHA и attempt; важные новые сценарии включены в проверки |
| Пакет готов к загрузке | Exact-CI artifact, ZIP digest, manifest, независимый профиль, provenance и production audit проверены |
| Пилот работает по имени | Реальная публикация и проверка публичных файлов; owner-approved ArNS Target; настоящая wallet-попытка и полное восстановление |

Успех одной строки не заменяет следующую. Скриншот синтетического кошелька или
успешная подстановка HTTP-ответов не доказывают работу расширения, расход,
финальную запись сети или доступность реального архива.

## Локальная проверка кандидата

Использовать проверенный Node 24.22.3 и установленные lockfile-зависимости. Основные команды:

```sh
npm test
npm run test:direct --prefix apps/web
npm run test:historical-native --prefix apps/web
npm run test:independent-unit --prefix apps/web
npm run test:offline-recovery
npm run lint --prefix apps/web

npm run arns:verify
npm run test:native-publication
npm run test:independent-browser
sudo -H env PLAYWRIGHT_BROWSERS_PATH="$HOME/.cache/ms-playwright" SEJIRE_TEST_OS_OFFLINE=1 \
  unshare --net "$(command -v node)" --test tools/recovery/browser.test.mjs

```

Полный `.github/workflows/checks.yml` также проверяет совместимость прежнего
funded-профиля, editor и runtime. Невозможность запустить Chromium в локальной

статуса. Неблокирующие dependency findings отражать отдельно.

Standalone HTML проверяется в Linux network namespace без внешних интерфейсов
и маршрутов. Путь Playwright в примере должен соответствовать папке установленных
браузеров; проверка состояния ядра не доверяет одной переменной окружения.
Подробнее о WebKit offline emulation и диагностике — в
[`tools/recovery/README.md`](../tools/recovery/README.md).

## Подготовка без ключа

Ручной workflow **Prepare Arweave-only SEJIRE publication (manual)** в
`.github/workflows/permaweb.yml` принимает точные `ci_run_id` и `ci_attempt`
для текущего HEAD рабочей ветки. Он предназначен только для подготовки и
публичной оценки native AR. Он получает exact-CI artifact без пересборки,
проверяет файлы и production dependencies, добавляет provenance. Ключи,
подписи, загрузка и изменение ArNS в этом workflow отсутствуют. Исторический
Turbo workflow отделён и не является путём публикации текущей ветки.

Артефакт независимого приложения называется **`permaweb-static-release`**.
Артефакт `permaweb-portable-funded-release` относится к прежней архитектуре.
Приёмка связывает source SHA, CI run/attempt, полный успешный набор проверок,
ZIP digest и размер, хеши файлов, профиль и граф реально включённых модулей.
Перед новой подписью native publisher повторно получает точный GitHub ZIP,
проверяет его digest и сравнивает его файлы с локальным принятым пакетом.
Одного редактируемого локального JSON с названием успешного CI недостаточно.

Принятый каталог по умолчанию — `.cache/permaweb-accepted`. Для чтения плана
и текущей цены на машине владельца:

```sh
npm run permaweb:plan
npm run permaweb:quote
```

`--release /absolute/path/to/accepted-pack` выбирает другой каталог, например
`npm run permaweb:plan -- --release /absolute/path/to/accepted-pack`.
Plan ничего не подписывает и не отправляет в сеть Arweave. Quote читает
`/info` и `/price`, считает native fee каждого файла и отдельного path manifest.
Лимит по умолчанию равен нулю; `withinBudget: false` в таком отчёте не означает
расход. Цена меняется, и старая оценка не является разрешением оплаты.

Пакет содержит `index.html`, идентичный `404.html`, `assets/`, `recovery/`,
`release-profile.json`, `bundle-boundary.json`, `release-manifest.json` и
`build-provenance.json`. `release-manifest.json` — локальная ведомость хешей,
а не Arweave path manifest. Публикация ZIP как одного файла не публикует сайт:
нужно загрузить содержимое корня, index=`index.html`, fallback=`404.html`.

## Публикация и имя

### 1. Проверить пакет и выбрать местный каталог журнала

Реальная загрузка выполняется после просмотра владельцем пакета, адреса своего
AR-кошелька и свежей цены. Native publisher запускается на **постоянном диске
компьютера владельца** с поддерживаемым Node 24.22.3 и Python 3 для безопасной
распаковки точного CI ZIP. Постоянный сервер для
работы сайта не нужен. Загрузка из временного GitHub Actions runner запрещена:
потеря такого runner не должна уничтожить единственную подписанную операцию.

Заранее выбрать отдельный приватный каталог для этого выпуска, расположенный
вне публикуемых файлов. При первой загрузке publisher создаёт его с правами
`0700`; уже существующий каталог не считается новым upload. Журнал содержит
подписанные операции, IDs, цену и проверку доставки. Не удалять его ради
повторной попытки и не использовать один каталог для разных выпусков.

### 2. Локальная авторизация и цена

Ключи и recovery phrase кошелька не передавать в чат, Git, публичную форму или
GitHub Actions. Этот CLI использует **локальный приватный JWK-файл владельца**,
а не текст из чата. Файл должен лежать вне checkout, release и journal, с правами
доступа только владельцу; путь задаётся в `NATIVE_ARWEAVE_JWK_FILE`. Экспорт и
работу с ключом выполняет сам владелец средствами своего кошелька. Кошелёк
обычного посетителя сайта работает через расширение: ему этот CLI не нужен.

Для новых подписей требуется доступ к exact-CI artifact в GitHub; если API
требует авторизацию, она задаётся локально через `GH_TOKEN`. Это проверка
происхождения пакета при выпуске, а не зависимость уже опубликованного сайта.

| Локальная настройка | Назначение |
| --- | --- |
| `NATIVE_ARWEAVE_NODE` | HTTPS origin native-узла; по умолчанию `https://arweave.net` |
| `NATIVE_MAX_REWARD_WINSTON` | Явный общий предел native fees целым числом; 1 AR = 10¹² winston |
| `NATIVE_UPLOAD_CONFIRM` | Для записи только точное `upload-native-arweave` |
| `NATIVE_ARWEAVE_JWK_FILE` | Путь к приватному локальному ключу; нужен для новых подписей |
| `GH_TOKEN` | Локальный доступ к GitHub artifact, если запрошен API; не публикуется |

Сумма лимита выбирается после текущей оценки. Код учитывает fees всех уже
подписанных файлов и незавершённых намерений подписи. Рост цены не повышает
лимит и не запускает пополнение кошелька автоматически. SOL и кредиты Turbo
этот publisher не использует.

### 3. Подписать и отправить native-транзакции

После настройки и явного решения владельца команда для **первого** запуска:

```sh
npm run deploy:permaweb -- --journal /absolute/private/path/sejire-release-journal
```

Каждый файл получает отдельную native Arweave format-2 transaction с нулевым
переводом получателю и согласованным storage reward. Намерение сохраняется
с `fsync` до подписи; точные подписанные байты — до первого сетевого POST.
Действует межпроцессная блокировка журнала. Заголовок и все chunks передаются
явно, в том числе для файла, помещающегося в один chunk.

Path manifest подписывается после подтверждения и получения точных байтов
всех его файлов. HTTP 200/202 от upload endpoint не считается подтверждённым
хранением. Состояние `AWAITING_CONFIRMATION_OR_DATA` и exit code `3` означают,
что требуется дождаться/проверить/продолжить **тот же** выпуск. Новый журнал
или новый платёж не являются автоматическим способом исправления.

### 4. Проверка и продолжение того же выпуска

| Команда с тем же `--journal` | Что она делает |
| --- | --- |
| `npm run permaweb:check -- --journal …` | Только читает сеть и обновляет местные результаты проверки; не подписывает и не отправляет chunks |
| `npm run permaweb:replay -- --journal …` | Явно повторяет уже подписанные заголовки и все chunks с прежними ID; не требует ключа или текущего GitHub HEAD и не создаёт подписей |
| `npm run permaweb:resume -- --journal …` | Продолжает выпуск и может подписать ещё не подготовленные файлы/manifest; повторно проверяет точный CI ZIP и общий лимит |

Во всех случаях указать первоначальный `NATIVE_MAX_REWARD_WINSTON`. Для replay
и resume дополнительно требуется `NATIVE_UPLOAD_CONFIRM`. Если исходный release
лежит в другом месте, снова передать `--release`.

Неизвестный результат подписи блокирует новую подпись. Сохранённый ACK не
доказывает, что узел удержал chunks: явное продолжение проверяет фактические
байты и при необходимости повторяет **ту же** операцию. При смене рабочей
ветки или недоступности GitHub можно ремонтировать уже подписанные операции
через replay. Это не даёт разрешения подписывать другой пакет.

### 5. Проверить публичный manifest до изменения имени

Полученный `MANIFEST_ID` сначала проверяется без изменения имени:

```sh
npm run permaweb:verify -- --manifest MANIFEST_ID
```

Если upload выполнялся с другим каталогом пакета, тот же каталог передать
проверке: `npm run permaweb:verify -- --manifest MANIFEST_ID --release /absolute/path/to/accepted-pack`.
Параметр `--release` поддерживается и командой `permaweb:verify-target`.

Проверка сравнивает каждый публичный файл, корневой адрес и реальный fallback
с принятым пакетом. Для HTML, CSS и JavaScript также проверяется Content-Type:
совпадение байтов само по себе не доказывает, что браузер сможет запустить сайт.
При временной недоступности сначала проверять уже известный ID и receipts,
не начинать новый upload автоматически.

### 6. Обновить существующее имя

ArNS сейчас имеет отдельный реестр/ANT в Solana. Поэтому **адрес `sejire.ar.io`
имеет дополнительную зависимость уровня имени**, хотя сайт и семейные архивы
записываются в Arweave. Прямой manifest/transaction ID нужно сохранить как
независимый способ доступа. Загрузка в Arweave сама по себе не меняет имя.

Затем владелец имени записывает прежний Target и меняет только корневую запись
`@` в [ar.io Console](https://console.ar.io/domains/sejire). Право изменения
зависит от owner/controller, а не от наличия AR-кошелька загрузчика. Проверить
стоимость и подтверждение в интерфейсе. Не покупать, не передавать, не освобождать
имя и не менять права в рамках обычного cutover. Текущий порядок описан в
[официальной инструкции Console](https://docs.ar.io/build/guides/working-with-arns/buy-manage-arns-console).

После обновления записи:

```sh
npm run permaweb:verify-target -- --manifest MANIFEST_ID
```

Сверка байтов по имени не доказывает саму owner-запись и L1 settlement. Эти поля
проверяются и записываются отдельно.

Состояние сети подтверждается через ответы выбранного узла; это не локальная
проверка консенсуса light client. Подпись, transaction ID, Merkle root и сами
байты проверяются отдельно. Доступ через разные шлюзы — проверка доступности
на момент запроса, без обещания связи из любой сети в любой момент.

## Реальная приёмка владельцем

Использовать небольшую синтетическую семью с несколькими деревьями и историей.
Зафиксировать публичные ID и хеши, без секретов:

1. Проверить desktop/mobile интерфейс, редактирование, отмену открытия версии,
   JSON/PDF и бесплатный encrypted backup.
2. В настоящем совместимом Arweave-расширении проверить выбранный адрес, цену,
   отказ и последующее явное подтверждение. Подпись делает владелец.
3. Продолжить сохранение после перезагрузки с тем же ID. Получить подтверждение
   и фактический ciphertext, проверить длину и SHA-256.
4. В чистом браузерном контексте восстановить весь vault. Отдельно открыть
   сохранённые `recovery.html` и encrypted kit без сети, сравнить все деревья,
   связи и историю. Слова SEJIRE вводит только владелец.
5. Сохранить независимые копии encrypted kit, signed operation/receipt,
   автономного decoder и описания формата. Слова хранить отдельно.

Смена origin не переносит IndexedDB/localStorage другого сайта. До cutover
сохранить данные прежнего браузера. Ранее оплаченный архив `AtwLYx509C9jWIFKUNg7dy1GSgiaDbXVK1YEQbBWfHY`
остаётся отдельным обязательством до проверки его фактических байтов и
восстановления. Новый AR-save не заменяет прежнюю оплату. Старые payload,
journals, signed transaction и receipt не удалять.

## Долгий срок

Открытый формат, статический decoder и независимые копии позволяют восстановление
без исходного сайта, Cloudflare, ArNS, SEJIRE backend или npm. Но существование
сети, носителей, имени, браузера, криптографии и ключей через 200 лет не доказуемо
этими тестами. Подробнее: [формат и границы восстановления](../tools/recovery/README.md).
