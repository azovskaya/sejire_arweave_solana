# Переносимый сервер SEJIRE и публикация `sejire.ar.io`

Этот пакет обслуживает **Solana Mainnet + промокод + серверную админку**. Статический сайт загружается в Arweave отдельно; Linux-сервис хранит журнал заказов и продолжает начатые сохранения. Работа сервиса не зависит от Cloudflare Workers, Durable Objects или платного бандлера. Наличие Dockerfile и успешной сборки само по себе не означает готовность работающего production-сервиса.

## Адреса и границы

| Назначение | Адрес / значение |
|---|---|
| Публичный сайт после переключения имени | `https://sejire.ar.io` |
| Основная админка | `https://sejire.ar.io/#/admin` |
| Прямой вход в управление фондом | `https://sejire.ar.io/#/fund-admin` |
| Обычное сохранение | `https://sejire.ar.io/#/save` |
| Восстановление | `https://sejire.ar.io/#/restore` |
| Управление самим именем | `https://console.ar.io/domains/sejire` |
| Запланированный API для этого профиля | `https://sejire-api.azovskaya.prod.page` |
| Профиль статического пакета | `portable-funded-mainnet` |
| Цена сохранения | `30000000` lamports = `0.03 SOL`; комиссия Solana отдельно |
| Максимальный зашифрованный архив всех деревьев | `524288` байт = `512 KiB` |

Адрес API указан как **планируемый** до его фактического создания и проверки. Если выбран другой хост, необходимо заново собрать клиент с его точным HTTPS origin и снова пройти CI: адрес API входит в неизменяемый опубликованный JavaScript. Ни пароль админки, ни treasury JWK, ни секрет промокода в клиент не включаются.

Сервисная оплата SOL и AR для долговременного хранения — разные средства. Сервер проверяет SOL-перевод, а затем сохраняет зашифрованный архив за AR из настроенного фонда. Промокод освобождает посетителя от платы за сервис; он расходует средства фонда. Необязательная помощь фонду открывается отдельным действием, по умолчанию равна нулю и не добавляется скрыто к цене.

## Что требуется на стороне владельца

1. Постоянно работающий Linux-хост или контейнерный хост с HTTPS, сохранением `/data`, достаточной памятью и свободным диском. Один SQLite writer и один executor. Нельзя запускать две независимые копии базы с одинаковым treasury signer.
2. Частная согласованная копия старого журнала и проверенное завершение передачи исполнения со старого сервиса. Снимок содержит токены доступа, зашифрованные архивы и подписанные транзакции; это **не публичный релизный артефакт**.
3. Доступ владельца к секретам прежнего сервиса. Treasury JWK и promo HMAC secret сохраняются при переносе; они не восстанавливаются из публичных адресов. Приватные ключи не вводятся в чат, не загружаются в Git и не публикуются в Arweave.
4. Подтверждённые публичные SOL-адреса получения сервисной платы и добровольных взносов. Они должны быть разными. Подпись владельца Solana нужна только для проверяемых им действий; сервер не получает приватный ключ посетителя.
5. Два работоспособных Mainnet RPC и подтверждённые серверные лимиты AR. Баланс и бюджет не заменяют друг друга. Повышение лимита в админке не создаёт AR.
6. Кошелёк, который действительно является Owner/Controller имени `sejire`, либо корректно связанная авторизация, показываемая текущей Console. Наличие Wander-сессии само по себе этого не доказывает.

Зафиксированный в текущем коде AR-адрес промокодного фонда: `qgoIFw9WsusMRapWzcFg4jNW08HSWvQkpAKOz86BUuI`. Оплачиваемое сохранение и промокод в этом релизе должны использовать соответствующий ему signer. Новый произвольный кошелёк вместо прежнего не подставляется молча.

## Сборка и первое включение без денежных операций

Из корня репозитория:

```bash
npm ci --prefix apps/sponsor
npm audit --prefix apps/sponsor --omit=dev --audit-level=high
npm run linux:build
npm run test:linux-package
docker build --pull --no-cache -f deployment/Dockerfile -t sejire-api:review .
```

Перед production deployment нужен свежий успешный audit production-зависимостей сервера: high/critical findings и ошибка получения audit должны остановить выпуск. Docker повторяет этот audit при установке production-зависимостей. `--no-cache` не позволяет использовать прежний успешный audit из кэшированного слоя, а `--pull` проверяет актуальный базовый образ указанной версии. Полный отчёт с dev/test dependencies сохраняется отдельно и не подменяет production audit. Manual portable workflow также заново проверяет production-зависимости web и sponsor перед публикацией.

Образ содержит Node.js 24.22.3, скомпилированный сервис и production-зависимости из lockfile. Он работает от непривилегированного пользователя `node`; встроенные admission/execution флаги выключены. Пример Compose открывает API только на `127.0.0.1:8787`; HTTPS завершает выбранный владельцем reverse proxy. Файл `sejire.env` создаётся **на хосте владельца** по `sejire.env.example` и не коммитится. Для секретов предпочтительна защищённая панель хостинга.

`/healthz` сообщает доступность процесса, тип runtime и `SEJIRE_BUILD_COMMIT`. Он не заявляет, что настроены деньги, промокод, миграция или внешние сети. `SEJIRE_BUILD_COMMIT` должен совпадать с фактически развернутым GitHub source SHA; это дополнительно сверяют с историей сборки хостинга.

### Настройки, которые нельзя угадывать

- `CHECKOUT_ALLOWED_ORIGINS`: точные разрешённые HTTPS origins, как минимум `https://sejire.ar.io`. Тестовый origin добавляют явно; `*` не используется.
- `SEJIRE_TRUSTED_PROXY_CIDRS`: только документированные адреса непосредственного reverse proxy. При пустой настройке пользовательский `X-Forwarded-For` не считается источником IP. Не устанавливать `0.0.0.0/0` или `::/0`.
- `CHECKOUT_PAID_AR_BUDGET_ID`: прежняя идентичность бюджета при переносе. Изменение ID не является способом обнулить потраченные средства.
- `CHECKOUT_PAID_AR_BUDGET_WINSTON`, `CHECKOUT_PAID_MAX_REWARD_WINSTON`: положительные целые суммы в winston; согласуются с реальным фондом и допустимой стоимостью одного архива.
- `CHECKOUT_SOLANA_RPC_URLS`: формат и все ограничения проверяются штатным RPC parser; не помещать приватный RPC token в браузерные `VITE_*` настройки.
- `CHECKOUT_CONTRIBUTION_ENABLED`: необязательная помощь фонду; не включается автоматически вместе с оплатой сохранений.

## Перенос прежних заказов

У старого Cloudflare Durable Object и новой SQLite нет автоматической общей базы. Публичные admin summaries не содержат всех данных и **не пригодны для миграции**. Требуется консистентный private snapshot всех прикладных таблиц, исходных ciphertext, unsigned/signed transaction bytes, idempotency keys, access-token hashes, reservations, treasury ceiling, расходов, настроек и alarm metadata.

Перед извлечением источника нужно остановить новые admissions и гарантировать отсутствие активных старых executors/alarms/in-flight подписей. Простое выключение приёма заказов не останавливает уже принятые обязательства. Экспорт нельзя делать параллельно с продолжающим работать писателем, а старый и новый signer нельзя оставлять исполняющими одни и те же задания одновременно.

Инструмент импорта принимает только новый путь базы, проверяет manifest/hash/counts/schema и создаёт обязательный барьер reconciliation. Ни текущая база, ни исходный snapshot не перезаписываются. Точные команды, source extraction и формат описаны в [инструкции миграции](../docs/verification/2026-11-25-publication-completion/backend/legacy-migration.md); выполняются только с частным источником владельца. В образе доступен `node build/import-ledger.mjs --snapshot PRIVATE.json --output NEW.sqlite --expected-sha256 SOURCE_DIGEST`. До успешной сверки миграция остаётся отдельным release blocker.

Особое прежнее обязательство нельзя потерять при переносе: архив `AtwLYx509C9jWIFKUNg7dy1GSgiaDbXVK1YEQbBWfHY`, ожидаемые `25269` байт, SHA-256 `96bb194c3fbcf1dfea7e738cf91d758b8cfdaabb5be934df8dacd96a65c7be85`. Исторический статус транзакции не заменяет проверку доступности и точных байтов. Не инициировать новый платёж или новый upload вместо восстановления исходной подписанной операции.

## Резервное копирование и восстановление

При заданном `SEJIRE_BACKUP_DIR` сервис делает online SQLite backup после старта и далее по интервалу, по умолчанию каждый час. Снимки включают согласованные committed WAL-данные, получают `quick_check`, SHA-256 manifest и права каталога `0700` / файлов `0600`. Удерживаются 48 последних проверенных снимков. Повреждённые или неизвестные файлы retention не удаляет.

```bash
# В контейнере из /app/apps/sponsor; пути на частном диске владельца:
node build/backup.mjs create /data/sejire.sqlite /data/backups
node build/backup.mjs verify /data/backups/ИМЯ_ПРОВЕРЕННОГО_СНИМКА
node build/backup.mjs restore /data/backups/ИМЯ_ПРОВЕРЕННОГО_СНИМКА /data/recovered/sejire.sqlite
```

Копия на том же диске защищает от отдельных логических сбоев, но не от потери всего хоста. Нужна отдельная защищённая off-host копия и пробное восстановление. Для переноса снимков не использовать публичные Actions artifacts, чат или Arweave.

Восстановленная база получает `.restore-review.json`. Сервис откажется стартовать, пока оператор не сопоставит её незавершённые обязательства с последующим состоянием сети/основной базы: старый snapshot может ещё не знать о реально совершённой подписи или оплате. После содержательной сверки предусмотрена команда:

```bash
node build/backup.mjs acknowledge /data/recovered/sejire.sqlite SHA256_БАЗЫ RECONCILIATION_REVIEWED
```

Это фиксирует **подтверждение оператора**, а не автоматически доказывает финансовую сверку. Нельзя использовать команду для обхода незавершённой проверки.

## Проверка production-сервиса перед публикацией

После миграции, настройки секретов, CORS/ingress и флагов приёма выполните read-only preflight с защищённо переданным админ-токеном:

```bash
# Не записывать сам токен в history, argv, Git или общий журнал.
SEJIRE_FUNDED_API_ORIGIN=https://sejire-api.azovskaya.prod.page \
SEJIRE_EXPECTED_SERVICE_COMMIT=ПОЛНЫЙ_ПРОВЕРЕННЫЙ_SHA \
npm run portable:service:verify
```

`SEJIRE_PREFLIGHT_ADMIN_TOKEN` передаётся через защищённое окружение владельца. Проверяются exact source, Mainnet, `0.03 SOL`, размер архива, CORS для `Authorization` и `Idempotency-Key`, закрытая админка, server configuration, public signer address, баланс/quote и бюджет фонда. Скрипт не вызывает sign/prepare, не создаёт заказы и не загружает данные. Его зелёный результат имеет scope `read-only-configuration-and-network`: реальное сохранение, миграция и доступность хоста проверяются отдельно.

### Реальная приёмка до необратимой публикации

Для приёмки не требуется предварительно загружать сайт в Arweave. Из успешного CI точного source SHA скачайте **`permaweb-portable-funded-release`**, сверьте artifact digest, `release-manifest.json` и hashes всех файлов. Разместите неизменённую распакованную папку на временном HTTPS origin или откройте её локальным HTTP-сервером на `http://127.0.0.1:8080`. `file://` не подходит для проверки модулей, Web Locks, CORS и кошелька. Пример команды из папки с `index.html`: `python3 -m http.server 8080 --bind 127.0.0.1`.

Владелец временно добавляет **точный** origin приёмки в `CHECKOUT_ALLOWED_ORIGINS` через запятую без пробелов, сохраняя `https://sejire.ar.io`. Клиент уже обращается к финальному HTTPS API; его JavaScript не пересобирают и API origin не подменяют. Штатный production preflight проверяет CORS для `https://sejire.ar.io`, поэтому временный origin и фактическую работу расширения кошелька проверяют дополнительно в браузере. После приёмки временный origin удаляют. Не переносят на production origin ключи и журналы через открытый канал: для отдельной тестовой семьи сохраняют штатный private recovery kit.

Владелец выполняет два end-to-end сохранения **с синтетической семьёй**: одно через настоящий Phantom/Solflare Mainnet, одно по промокоду. В обоих случаях проверяют квитанцию, точный ciphertext digest/size, фактическую доступность raw bytes и восстановление на чистом origin/в автономном recovery. Затем меняют промокод, проверяют отказ старого кода для новых заказов и продолжение уже принятого старого заказа. При неизвестном результате продолжают ту же операцию, не нажимают «заплатить заново».

## Статический пакет и обновление купленного имени

```bash
SEJIRE_FUNDED_API_ORIGIN=https://sejire-api.azovskaya.prod.page npm run arns:build:portable
npm run arns:verify:portable
node scripts/prepare-permaweb.mjs apps/web/dist .cache/permaweb-portable-release
```

В Arweave загружается только готовая статическая папка с `index.html`, `assets`, fallback и recovery kit. Весь ZIP исходного репозитория, backend, SQLite, `.env`, приватные snapshots и ключи туда не загружаются. CI сохраняет artifact `permaweb-portable-funded-release` отдельно от independent direct-Arweave варианта. Его manifest связывает файлы с source SHA и точными hashes; каждый JS chunk проверяется, recovery kit обязателен, публичный `admin-lock.json` запрещён. Independent gate не заменяет проверку SOL/promo релиза.

Ручной workflow `.github/workflows/permaweb-portable.yml` сначала восстанавливает **точный** artifact успешного CI текущего head ветки `feat/funded-portable-release-20261125`. Режим `prepare` создаёт reviewable pack/quote без ключа. Режим `upload` требует отдельного подтверждения владельца, свежего API preflight и отмеченных проверок миграции, always-on/restore и реальных сохранений. По умолчанию лимит quote равен нулю; автоматического пополнения credits нет. Повторить неоднозначный upload с новой подписью автоматически нельзя. Ключ загрузки, если выбран Actions, владелец вводит только в GitHub Secrets; при загрузке через Console ключ остаётся в его кошельке.

**Доступность ручного workflow — отдельная проверка.** GitHub показывает `Run workflow`, когда файл зарегистрирован в default branch. На проверенном `main` (`897559c197bc90ae9fac66abaefe000df2a2b51c`, 25 ноября 2026) нового `permaweb-portable.yml` ещё нет. Для этого пути требуется отдельный reviewed merge файла регистрации; нельзя обещать доступную кнопку только по наличию файла в feature branch. Сам запуск затем выбирает точную проверенную feature branch. В режиме `prepare` обязательное поле `service_commit` заполняют полным source SHA кандидата; это поле само по себе не означает, что API уже развёрнут. Скачивание CI artifact и описанная выше приёмка не требуют регистрации upload workflow. При выборе загрузки через Console сохраняются те же acceptance, file-hash, quote и public-byte проверки.

Подготовлен [draft PR № 12](https://github.com/azovskaya/sejire_arweave_solana/pull/12), содержащий только регистрацию этого workflow. Сам PR не слит; его слияние не запускает upload, поскольку trigger ручной, а job допускает только указанную feature branch. Отмеченные в форме owner acceptance — подтверждения запускающего владельца, а не независимые автоматические доказательства миграции или реальной оплаты.

После загрузки сначала проверяются публичные файлы, manifest, MIME, относительные assets и fallback, затем сайт открывается по manifest transaction ID. Только после этого владелец открывает `https://console.ar.io/domains/sejire`, записывает прежний `@` Target/TTL и Owner/Controllers, редактирует **корневую запись `@`**, вставляет новый **manifest TX ID** и подтверждает показанную операцию. Имя покупать повторно не нужно. Изменение имени не удаляет прежние публикации. Для отката интерфейса возвращают прежний Target, сохраняя работающий сервер для всех уже начатых обязательств.
