## Что выяснено о хостинге

Официальная [страница тарифов](https://blitz.cloud/pricing/), обновлённая 26 ноября, предлагает один постоянно работающий Pro app: 512 MB за €3/месяц или €30/год, 1 GB за €5/месяц или €50/год. Pro всего аккаунта — €9/месяц или €90/год. Это варианты для выбора владельцем; подписка не оформлена. Достаточность минимального размера проверяется на реальном хосте. Free засыпает через 30 минут, программные API-запросы его не будят. Для фонового продолжения обязательств Free не подходит.

Nightly file backups документированы для аккаунтного Pro. Их включение в отдельный Pro app не подтверждено; необходимо проверить эту функцию либо организовать собственную частную внешнюю копию согласованных снимков. PostgreSQL создавать не нужно: принятый сервис использует SQLite в `/data`.

### Три настройки перед первым build

[GitHub deployment guide](https://blitz.cloud/docs/deploy-from-github/) описывает отдельные механизмы, которые нельзя объединять в один переключатель:

1. Включить **Only use my Dockerfile**. Иначе после build/start failure платформа может собрать собственный Dockerfile без изменения файла в Git.
2. Выключить **Deploy every push**. `autoUpdate:false` в подключённом средстве управления относится к ночным обновлениям; этого недостаточно для отключения push-trigger.
3. Проверить **Build on your own GitHub Actions** и общую настройку **Also build my new apps on my own GitHub Actions**. Этот режим добавляет workflow commit в выбранную ветку. Принятый source не должен измениться. Официальные pricing и deployment pages расходятся в описании значения по умолчанию для Free; необходима фактическая проверка панели.

Текущие `apps_deploy_github` и `apps_update` не принимают эти три поля. Поэтому один вызов deploy не закрывает условия. Сначала проверить доступные настройки в панели. Если строгий Docker режим можно включить только после создания, первый запуск допускается рассматривать исключительно как пустую проверку хоста без ключей/старого состояния; его результат не принимается как production build до строгой повторной сборки и сверки. Не передавать сюда `main` или docs-ветку.

Даже выключенные push/nightly updates не доказывают отсутствие внеплановых security rebuild платформы. Для каждого нового образа нужны provenance, свежий audit и проверка единственного исполнителя.

## Первое создание: только пустая база

После проверки перечисленных условий использовать `createArguments` из JSON. `folder` отсутствует намеренно: Dockerfile копирует файлы из нескольких директорий корня. В build history должны быть точный source, наш Dockerfile и успешный audit production-зависимостей. Для повторного build не принимать старый cached audit за свежий; выбрать rebuild без кеша либо выполнить свежий audit отдельно до включения.

До любых секретов, старой базы или real-wallet тестов:

1. Убедиться, что создано именно новое SEJIRE app, а не изменено другое приложение.
2. Сверить actual checkout SHA и Dockerfile. Значение `SEJIRE_BUILD_COMMIT` — только метка окружения, не независимое доказательство кода.
3. Убедиться, что `/data` сохранён платформой **с первого запуска** и доступен непривилегированному `node`. Добавление kept folder позднее не переносит старые файлы в него автоматически; это описано в [settings/files](https://blitz.cloud/docs/settings-and-files/).
4. Применить [bootstrap.env.example](bootstrap.env.example). Он содержит только публичные параметры. Все новые admissions/execution выключены. `ADMIN_TOKEN`, `PROMO_CODE_SECRET`, `ARWEAVE_TREASURY_JWK` отсутствуют; приватные snapshots не загружаются.
5. Установить порт `8787`, `gateErrors:false`, `autoUpdate:false`. Отдельно проверить dashboard push/Docker настройки. `gateErrors:false` нужен, чтобы API сохранял собственные JSON-ошибки, а не HTML страницы хостинга ([HTTPS guide](https://blitz.cloud/docs/addresses-and-https/)).
6. После фактического выбора always-on тарифа установить/сверить `keepAwake:true`. Не считать наличие платного тарифа доказательством конкретного значения настройки.

Подключённый `env_set` перезапускает приложение после каждого изменения; не применять секреты или новый путь старой базы серией таких операций к уже исполняющему журналу. Закрытый пустой bootstrap допускает эти перезапуски, действующий финансовый сервис требует согласованного maintenance-порядка.

## Проверка закрытого HTTP-контура

Из операторского checkout на Node 24:

```bash
node deployment/blitz/verify-closed-bootstrap.mjs \
  --expected-commit ef0252025c32687dce018368ea94d74af2728c66
```

Скрипт обращается к запланированному API только методами GET/OPTIONS. Он не получает admin token, не создаёт заказы, не вызывает prepare/sign/upload и не исправляет настройки. Проверяет точный source label, закрытые offers, отсутствие готового promo fund, отказ неавторизованной админке, CORS и ограниченный JSON. Redirect или HTML вместо API являются ошибками.

На пустой установке без `PROMO_CODE_SECRET` ожидается `503 fund_not_configured`, а OPTIONS нового checkout order закрыт до CORS. Это проверенные контракты текущего API; не открывать платежи для получения более удобного HTTP-ответа.

Успех имеет scope **credential-free-closed-http-boundary**. Он не доказывает пустоту базы, отсутствие фоновых операций, действительный build SHA, доступность фонда, migration, always-on, filesystem locking или real-wallet acceptance. Эти условия проверяются отдельно. Некоторые GET обновляют штатные rate counters; инструмент не доказывает побитовую неизменность SQLite. Не запускать этот probe как доказательство безопасной остановки импортированного ledger.

## Обязательные проверки на самом хосте

Они выполняются на синтетической пустой установке до переноса денег и старых обязательств:

| Проверка | Доказательство, которое нужно получить |
|---|---|
| Постоянный диск | App metadata показывает `/data`; синтетический marker и проверенный SQLite snapshot сохраняются после restart. Права `/data` и snapshots соответствуют текущему `USER node` и требованиям приватности |
| Единственный writer | Второй процесс для того же **синтетического** пути получает `backend_writer_already_active`; первый остаётся исправен |
| Смена версии | Подтверждён stop-before-start для executor и одна общая актуальная база; никаких параллельно исполняемых cloned volumes |
| Завершение | SIGTERM завершает requests, alarms, backups и background tasks до освобождения guard; фактический grace period достаточен |
| Сеть | HTTPS, корректные JSON-ошибки, CORS, лимиты тела/таймауты; источники ingress подтверждены, пользовательский X-Forwarded-For не позволяет менять свою идентичность |
| Ресурсы | Измерены RAM/disk при максимальном 512 KiB ciphertext, параллельных обращениях и backup; нет OOM/restart и нехватки места |
| Внешняя копия | Частно сохранён штатный согласованный snapshot; восстановление в новый путь даёт review marker и проходит сверку до запуска |

**Почему нужен отдельный rollout test.** Blitz документирует работу старой версии до готовности новой. При общей базе наш writer guard должен запретить второй процесс — это безопасно для журнала, но обычный rolling deploy может не состояться. При отдельных копиях диска локальный guard не защищает от двух исполнителей. Публичные документы не подтверждают stop-before-start, точные lock semantics и grace period для этой установки. Это инженерный вывод из deployment guide и кода, а не установленный дефект хоста.

`SEJIRE_TRUSTED_PROXY_CIDRS` пока пуст: это не доверяет произвольным forwarding headers. Для production нужно определить адреса непосредственного proxy и его контракт. Иначе посетители могут делить один IP rate-limit bucket. Не использовать глобальные CIDR или угаданные внутренние сети. Если хост не может дать подходящий ingress и единственного executor, его нельзя принимать для этого выпуска; другой API origin потребует нового клиентского build и CI.

## Старые операции: выключенные флаги не являются остановкой

Новый приём, выполнение AR upload и продолжение уже подписанных операций — разные механизмы. Promo alarm продолжает принятые jobs; paid runner может перед проверкой `CHECKOUT_PAID_EXECUTION_ENABLED` отправить уже сохранённые signed SOL bytes. Это поддерживает ранее принятые обязательства и **не разрешает запускать несогласованную копию базы**.

Реальный импорт выполняется штатным инструментом в новый путь, например `/data/sejire-migrated.sqlite`; исходную bootstrap DB не перезаписывать. У импортированной базы остаётся `.restore-review.json`. Не переключать запущенный процесс на этот путь и не снимать marker, пока прежний executor действительно не остановлен, не завершена private reconciliation и не зафиксирована передача единственному исполнителю. Конкретный порядок — в уже проверенном legacy-export pack.

После передачи сохранить прежние promo HMAC secret, signer, получателей и budget identity. Уже записанные в старом Fund Admin SOL recipients сначала извлекаются и сверяются как часть migration; их отсутствие в публичном Git не означает, что владелец обязан придумывать новые адреса. Прежнее unresolved обязательство `AtwLYx509C9jWIFKUNg7dy1GSgiaDbXVK1YEQbBWfHY` остаётся в журнале и не заменяется новым платежом.

## Backup и переход к публикации

Встроенные `/data/backups` находятся на том же хосте. Для внешней копии выгружается завершённый проверенный snapshot с manifest, не работающий SQLite-файл отдельно от WAL. Восстановление — через штатный SEJIRE restore в новый путь и reconciliation.

Обычная кнопка [Blitz Restore app files](https://blitz.cloud/docs/backups/) заменяет kept folders и автоматически запускает приложение. Для финансового ledger это не замена контролируемому SEJIRE restore: старый snapshot может не знать о более позднем переводе. Не восстанавливать рабочую базу этой кнопкой без предварительно обеспеченного остановленного executor и review barrier.

После host/migration/configuration gates выполняются существующий authenticated `portable:service:verify`, реальные Mainnet SOL и promo roundtrips с синтетической семьёй, raw byte/digest проверки и чистое/offline восстановление. Только затем принятую статическую папку можно загрузить в Arweave и после проверки manifest поменять запись `@` существующего имени. Админка после cutover: `https://sejire.ar.io/#/admin`, фонд: `https://sejire.ar.io/#/fund-admin`.

Первое необходимое действие владельца сейчас — вход в существующую панель Blitz для фактических deployment settings и выбора always-on. ArNS и кошелёк понадобятся после готовности сервера. Восстановительные слова и секреты не являются входными данными этого операторского комплекта.
